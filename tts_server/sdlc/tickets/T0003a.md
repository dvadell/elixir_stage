----
title: Serialized FIFO queue + timeouts (serialize synthesis, bound, 429/500)
----

onnxruntime is single-threaded per session: two concurrent `synthesize` calls
trample the shared pipeline. Implement the real serialized FIFO queue in
`src/queue.mjs` (T0001 skeleton), bound it, and enforce the per-request timeout
so a hung inference never hangs the service or other clients. Split out of the
former T0003; graceful shutdown (drain) and the model-cache/worker_threads notes
are T0003b and T0003c.

## Desired architecture

```text
request -> queue (bounded, FIFO) -> synthesize (one at a time) -> respond
              |                        |-- timeout (TTS_SYNTH_TIMEOUT_MS)
              `-- queue full -> 429    `-- failure -> 500
```

## Scope

### 1. Serialized FIFO queue (`src/queue.mjs`)

- Implement `Queue.enqueue(job)` / `pending()` (the T0001 skeleton throws
  `not_implemented`): one synthesis in flight, the rest wait FIFO.
- Bound `TTS_MAX_QUEUE` (default 8, config already wired); when full, reject the
  new request immediately with **429 `busy`** (JSON per `PRD.md` §7) — never
  make a client wait behind an unbounded backlog.
- Each queued item carries a `requestId` used across logs (the per-request
  latency breakdown in T0005 builds on it).
- `QueueError` already carries `code: "queue_full" | "synth_timeout"`; map them
  to HTTP 429 `busy` and 500 `synthesis_failed` respectively.

### 2. Timeouts & failure isolation

- Per-synthesis timeout `TTS_SYNTH_TIMEOUT_MS` (default 30 s): on expiry, log a
  warning with request id + synth duration, reject that job with 500
  `synthesis_failed`, and continue with the next item. **A hung inference never
  hangs the service or other clients.**
- Synthesis errors are isolated per request; a crash in the pipeline wrapper
  must not take down the process (wrap and recover; the process itself only
  exits on SIGTERM — see T0003b).

### 3. Wire into `src/server.mjs`

- Route `POST /v1/tts` through the queue instead of calling `tts.synthesize`
  directly (replaces the inline comment at `server.mjs`).
- Add the `requestId` to the existing success/failure log lines.
- Saturation and timeout log lines: `queue full -> 429` / `synthesis timed out`
  (surface these in T0005's structured-log formalization).

## Acceptance criteria

- [ ] Concurrent requests serialize correctly; audio responses are all correct
      (no interleaving/corruption); logs show non-overlapping `synthMs`.
- [ ] Exceeding `TTS_MAX_QUEUE` returns 429 `busy` promptly (JSON error body).
- [ ] A stalled synthesis (simulated via a test hook) returns 500
      `synthesis_failed` after `TTS_SYNTH_TIMEOUT_MS` and the next queued
      request still succeeds.
- [ ] A failing synthesis is isolated: the process stays up and serves the next
      request.
- [ ] Every request path terminates (200/4xx/5xx) — no hanging clients.

## Verification

- Fire N concurrent `curl`/`node:test` requests; assert all get valid WAVs and
  that logs show serialized `synthMs` (no overlap).
- Set `TTS_MAX_QUEUE=1` and saturate; assert 429 on overflow.
- Inject a fake slow synthesis (test hook) and assert the timeout path (500,
  next request succeeds).
- `node test/api.test.mjs`; from the umbrella root, `mix precommit`.
