----
title: Observability + benchmark (structured logs, latency metrics, load test, memory)
----

Make the TTS pod observable and prove its latency/memory budget on the real
deployment. Structured logs with per-request latency breakdown already exist in
skeleton form (T0001–T0003); this ticket formalizes them, adds a lightweight
metrics endpoint, and runs a repeatable benchmark that records the numbers into
`TECHNICAL_NOTES.md` and tunes the k8s resource requests (T0004).

## Scope

### 1. Structured logging

- One log line per request:
  `{level: info, msg: "synthesized", requestId, model, queueWaitMs, synthMs,
  encodeMs, totalMs, bytes, durationMs}`.
- Warnings on timeout (`synthesis timed out`), saturation (`queue full -> 429`),
  and shutdown drain.
- **Do not log full text by default** — log text length + request id only
  (privacy, untrusted input).

### 2. Metrics

- `GET /metrics` (Prometheus text format) exposing at minimum:
  - `tts_requests_total{status}` — counter.
  - `tts_synthesis_duration_seconds` — histogram (or summary): total per request.
  - `tts_queue_wait_seconds` — histogram.
  - `tts_queue_length` — gauge.
  - `tts_ready` — gauge (0/1).
- Implemented with `node:http` + manual counter/histogram arrays — no monitoring
  framework dependency (keep the image lean). Prometheus scrapes the pod.

### 3. Benchmark (reference pod, CPU)

- Methodology (mirror T0008): fixed Spanish sentence, 3-run median, cold vs
  warm cache.
- Metrics: model load time, primed synthesis latency (p50/p95),
  synthesis ratio, download size, RSS memory after load and after a burst of
  requests, queue behavior under N concurrent requests.
- Record the results in a `Benchmarks` section of `TECHNICAL_NOTES.md` and
  update the resource requests/limits in `deploy/deployment.yaml` (T0004) if
  the measured footprint differs materially.

### 4. Load test

- A small `node:test`/script-based load test (`test/load.mjs`): fire K
  concurrent requests against the pod, assert no 5xx under nominal load, and
  report p50/p95 latency. Include a saturation case that asserts 429s appear
  once the queue bound is exceeded.

## Acceptance criteria

- [ ] Every request produces a structured log line with the latency breakdown.
- [ ] `/metrics` exposes the counters/gauges above and is scrapable.
- [ ] Benchmark numbers (load, p50/p95 synthesis, memory, ratio) recorded in
      `TECHNICAL_NOTES.md`.
- [ ] Resource requests/limits in `deploy/deployment.yaml` reflect the measured
      numbers.
- [ ] Load test shows no hangs and no 5xx under nominal load; 429 behavior
      confirmed under saturation.
- [ ] Full text is never logged.

## Verification

- `curl :8080/metrics | rg tts_` — counters increment across requests.
- Run `node test/load.mjs` with `TTS_MAX_QUEUE=2` and a burst; observe 429s +
      latency histogram.
- Watch RSS in the pod (`kubectl top pod`) during a burst; record peak.
- From the umbrella root, `mix precommit` (no Phoenix changes expected).
