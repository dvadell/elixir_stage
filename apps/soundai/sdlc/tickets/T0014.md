----
title: Audio reply endpoint — POST /api/conversations/audio
----

Add the **audio mode**: one server round trip that runs the LLM (via the T0013
seam) and synthesizes the answer with the in-process Elixir TTS
(`Soundai.TTS`/Ortex), returning the WAV directly. The browser plays it instead
of speaking text.

## Desired flow

```text
Browser (audio mode = TTS engine "server")
  | POST /api/conversations/audio  {text, language}   (+ soundai_conversation cookie)
  v
ConversationAudioController
  | Soundai.Conversation.submit_transcript(text, conversation_id)   (LLM)
  | Soundai.TTS.synthesize(response_text, language)                 (Ortex/VITS)
  v
200 audio/wav bytes
  + headers: X-Conversation-Id, X-TTS-Duration-Ms, X-TTS-Model
  + Set-Cookie: soundai_conversation=<id>
```

## Scope

### 1. Route + controller

- `router.ex` (under the existing `/api` scope, `:api` pipeline — add
  `fetch_cookies` there as in T0013):

  ```elixir
  post "/conversations/audio", ConversationAudioController, :create
  ```

- New `SoundaiWeb.ConversationAudioController`:
  - Validates `text` (non-empty, ≤ 4000) and optional `language` (default
    `"spanish"`), reusing `Soundai.Conversation` validation.
  - Reads `conversation_id` (body param > cookie), calls
    `Soundai.Conversation.submit_transcript/2`.
  - Synthesizes via `Soundai.TTS.synthesize(response_text, language)`.
  - On success: `put_resp_cookie("soundai_conversation", id, ...)`,
    `put_resp_header("X-Conversation-Id", id)`, plus the TTS headers, send
    `conn |> put_status(:ok) |> send_resp(200, wav.audio)`.
  - **503** when `Soundai.TTS` is not enabled (no model file) — the browser
    falls back to text mode (T0015). **422** for invalid/oversized text or a
    response too long for TTS (`Soundai.TTS.validate_text`). **502/504** for
    LLM failure (same mapping as T0013).

### 2. Error semantics (graceful failure, PRD §13/§5)

- The endpoint must never return a 500 for expected failures. LLM down and TTS
  down are distinct, quiet-client recoverable errors.
- LLM success + TTS failure: client already has the fallback path (speak the
  text with native engine). Return the failure code plus (optionally) the
  response text in a small JSON body so the client can fall back without a
  second LLM call — decide and document; simplest is a 4xx/5xx JSON with the
  text, client falls back to text mode only when no text is available.

### 3. Tests

- `ConversationAudioControllerTest` with both the fake LLM adapter and the
  `TTSFakeAdapter` (already injected into `Soundai.TTS`):
  - valid → 200 `audio/wav`, `X-Conversation-Id` set and cookie set;
  - TTS disabled (model absent) → 503;
  - missing/blank/oversized text → 422;
  - LLM error → 502/504 JSON.

## Acceptance criteria

- [ ] `POST /api/conversations/audio` returns WAV bytes for a valid transcript,
      with `X-Conversation-Id` and `Set-Cookie: soundai_conversation`.
- [ ] Context is shared with the text endpoint: a follow-up via this endpoint
      after a text-mode turn (same cookie) resolves in context.
- [ ] 503 when the server TTS model is absent; 422 on validation; 502/504 on
      LLM failure — all without a 500.
- [ ] `Soundai.Conversation` is reused unchanged (single LLM seam).
