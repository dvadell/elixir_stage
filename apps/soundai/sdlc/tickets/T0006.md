----
title: Pluggable TTS engine architecture + native engine + settings picker
----

Introduce the **pluggable TTS engine** foundation behind the voice assistant's
`speaking` step, **without changing behavior**: the browser still speaks the
server `response` aloud via the native Web Speech API (`speechSynthesis`), but
the code now routes through a small engine abstraction that a follow-up ticket
(T0007) fills with a local Transformers.js model. This ticket is the safe
rehearsal: by the time it ships, the assistant sounds exactly as it does today.

It also ships the **user-facing picker**: `/settings` gains a text-to-speech
select (local model options listed, native API last) persisted in a
`soundai_tts` cookie, with the same precedence rules the STT model uses.

The product loop stays `... sending -> speaking -> result`; only *how* the text
becomes audio is refactored.

## Desired architecture

```text
Browser
  |
  | server response text
  v
voice_assistant.js (speakResponse)
  |
  v
createTTSEngine(engineId)      <- tts_engine.js registry
  |
  +--> native (only engine this ticket)
         |
         v
      speechSynthesis -> speaker
```

The `transformers` engine branch is stubbed: any engine id that is not
implemented yet resolves to the native engine (identical behavior today), so
the registry interface is exercised before the real local backend lands.

## Scope

### 1. TTS engine registry — modular by design

- New `apps/soundai/assets/js/tts_engine.js` exporting:
  - A **common engine interface** each engine implements:
    - `init()` → Promise; preloads whatever the engine needs (voices today,
      model weights in T0007).
    - `isReady()` → bool.
    - `speak(text, language, {onend, onerror})` → starts playback; resolves
      `onend` when playback finishes, `onerror` on failure.
    - `cancel()` → stops any in-flight synthesis/playback immediately.
  - **`createTTSEngine(engineId)`** registry/factory returning an engine
    instance. This ticket registers only the **`native`** engine; any unknown
    or not-yet-implemented id logs a warning and returns the native engine, so
    `voice_assistant.js` never knows which backend is active.
  - Future engines (local transformers.js in T0007, server TTS later) are added
    by registering a class here — no changes to `voice_assistant.js` or the UI.

### 2. Native engine — pure move

- New `native` engine class in `tts_engine.js` that wraps the current
  `speechSynthesis` code from `voice_assistant.js::speakResponse`
  (utterance + `languageToBCP47`-derived lang + language-aware voice pick from
  `getVoices()`), moved verbatim with no behavioral change.
- `speechSynthesis.getVoices()` fires asynchronously — have `init()` warm it so
  the first utterance is not delayed.
- The native engine remains the **automatic fallback** for any local-engine
  failure once T0007 lands (see §4 of T0007).

### 3. Wire the engine into the voice assistant

- In `voice_assistant.js`, replace direct `speechSynthesis` calls with the
  engine abstraction:
  - `resolveConfig` gains a `tts` key resolved with the standard precedence
    (see §5).
  - On boot, resolve the engine id and call `createTTSEngine(engineId)`, storing
    the instance on the controller.
  - `speakResponse(responseText)` calls `ttsEngine.speak(...)` instead of
    constructing an `SpeechSynthesisUtterance` directly; keep the `speaking`
    state and `onend` → `result` transition, and the existing quiet-note
    behavior when speech is unsupported.
  - `pointerdown` calls `this.ttsEngine.cancel()` (replacing the direct
    `speechSynthesis.cancel()`), so interruption behavior is unchanged.
  - If no engine is selectable at all (unsupported browser), degrade to the
    transcript + quiet note exactly as today.
- Since only the native engine is registered in this ticket, end-to-end behavior
  is byte-for-byte the same as today.

### 4. Config selection precedence

- New cookie `soundai_tts` holding the engine id, written by `/settings`
  exactly like `soundai_model` (URL-encoded, `path=/; max-age=31536000;
  SameSite=Lax`).
- Precedence at load: **URL param (`?tts=...`) > cookie > default engine**.
- Reuse the existing `readCookie` helper in `voice_assistant.js`.

### 5. Settings page: TTS model picker

- `apps/soundai/lib/soundai_web/controllers/settings_html.ex`: add `@tts_models`
  (mirror `@models`), listing:
  1. `Xenova/mms-tts-spa` — "MMS Español — balanced" (Spanish VITS; implemented
     in T0007).
  2. `onnx-community/Supertonic-TTS-2-ONNX` — "Supertonic 2 — best quality"
     (experimental, larger download; benchmarked in T0008).
  3. `native` — **"Voz nativa del sistema"** (the browser's built-in voices; no
     download). **Must be the last option.**
  - Each option carries `data-label` and `data-desc` so the client renders the
    description and the "Saved" confirmation without the server (as today).
  - Until T0007 ships, selecting a local option still speaks with the native
    engine (via the registry fallback) — acceptable, and keeps the picker
    data-driven from day one.
- `apps/soundai/lib/soundai_web/controllers/settings_html/index.html.heex`: add a
  second `<select id="tts-model">` below the STT one, reusing the same markup
  pattern with unique ids (`tts-model`, `tts-model-desc`, `tts-saved` /
  `tts-saved-text`). Update the page heading/copy so it covers both speech
  models; keep it simple and accessible.
- `apps/soundai/assets/js/settings.js`: generalize the cookie/select/
  description/saved logic so it is shared, and add a `mountTTSSettings` (or a
  single `mountSettings` handling both selects) that reads/writes the
  `soundai_tts` cookie with identical behavior. Mount it from `app.js`.

### 6. Security & privacy

- No new server endpoints; no audio or text beyond the existing
  `POST /api/transcriptions` call. The `response` text is spoken locally and
  never uploaded.
- TTS text is untrusted server/LLM output — it is rendered to audio only, never
  evaluated as code.

### 7. Documentation

- Update `apps/soundai/sdlc/TECHNICAL_DESCRIPTION.md`:
  - Architecture: note the new pluggable TTS engine (`tts_engine.js`) behind the
    `speaking` step; native engine is the only backend for now, local follows.
  - Repository layout: add `tts_engine.js`.
  - Settings section: document the TTS select and the `soundai_tts` cookie.
  - §12's "keep the configs in sync" note: extend to cover
    `TTS_CONFIG`/`@tts_models` (TTS_CONFIG lands in T0007; the note can be added
    now and applied then).

## Acceptance criteria

- [ ] `/settings` renders a second select (`#tts-model`) listing the two local
      model options plus the native API as the **last** option, each with
      `data-label` and `data-desc`.
- [ ] The `soundai_tts` cookie is read/written from `/settings` with the same
      behavior as `soundai_model`; the saved confirmation shows the selected
      engine.
- [ ] Selection precedence is `?tts=... > soundai_tts cookie > default`.
- [ ] `voice_assistant.js` routes all speech through `createTTSEngine` /
      `ttsEngine.speak`; no direct `speechSynthesis` usage remains in the
      controller.
- [ ] With only the native engine registered, speaking works exactly as before
      (Spanish voice pick, `speaking` state, `onend` → `result`).
- [ ] Starting a new recording cancels in-flight speech (via `ttsEngine.cancel`).
- [ ] Unimplemented engine ids fall back to native with a console warning (no
      error state, no crash).
- [ ] Unsupported-browser behavior (transcript + quiet note) is unchanged.
- [ ] Adding a new engine later requires only registering a class in the
      registry — no changes to `voice_assistant.js` or the UI.
- [ ] `TECHNICAL_DESCRIPTION.md` reflects the engine abstraction and settings
      picker.
