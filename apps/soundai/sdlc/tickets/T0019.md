----
title: Spike — Authentication, authorization & rate limiting for the public voice API
----

**Spike (time-boxed research, no production code).** The three API endpoints
that trigger expensive work — `POST /api/transcriptions` (LLM),
`POST /api/conversations/audio` (LLM + TTS), and `POST /api/tts`
(ONNX inference) — are intentionally unauthenticated, publicly reachable, and
unlimited. Until this is resolved they are an open DoS / cost vector, and the
conversation store can be tampered with cross-client. This is acknowledged in
the code headers, PRD §14 and the README status ("Authentication",
"Rate limiting" unchecked).

## Problem

- Any client can burn LLM tokens and CPU-bound ONNX synthesis at will; a
  single GenServer serializes all TTS, so a few junk requests starve real
  users (`tts_controller.ex`, `conversation_audio_controller.ex`,
  `transcription_controller.ex`).
- `conversation_id` is fully client-controlled: the body param wins over the
  server cookie (`transcription_controller.ex:76`), and `reset: true` deletes
  the stored context for any id an attacker can supply/guess
  (`resolve_conversation_id/2`) — cross-user context tampering/deletion.
- Part of authentication currently happens **at the SSL terminator / reverse
  proxy, outside this project** (e.g. ingress basic-auth or IP filtering).
  Whatever we build in-app must compose with that layer instead of duplicating
  or fighting it.

## Spike scope (deliverable = written decision + follow-up tickets)

1. **Inventory the terminator**: what does it already give us (TLS client
   auth? basic auth? IP allowlist? header injection like `X-Forwarded-For`
   sanitization)? Where is the trust boundary between proxy and Phoenix?
2. **Rate limiting design**: candidate libraries (`PlugAttack`, `ExRated`)
   vs terminator-level limits; keying strategy (client IP behind a proxy —
   beware spoofable `X-Forwarded-For`; per-conversation-id); sensible limits
   per endpoint class (TTS is CPU-heavier than text mode); burst vs sustained.
3. **Conversation-id ownership model**: stop trusting the body param — either
   accept only the server-set signed cookie, or sign/HMAC the id so foreign
   ids are rejected; make `reset` operate only on ids provably owned by the
   caller. Decide what "ownership" means pre-authentication (cookie bearer).
4. **AuthN/AuthZ options** ranked by effort: none-but-rate-limited (public
   demo), shared-secret/bearer for API clients, cookie-session auth for the
   UI, deferring to terminator auth with an internal "trusted proxy" plug.
   Recommend one for near-term deployment and one target state.
5. **Abuse guards beyond rate limiting**: request-body size caps
   (`Plug.Parsers` options), transcript length caps (see T0025), concurrent
   TTS queue depth limit.
6. **Rollout plan**: config-driven (off in dev/test), metrics to watch,
   failure mode for limited clients (429 + Spanish quiet note on the client).

Output: a short ADR-style doc in `sdlc/` plus one or more implementation
tickets split out of this spike.

## Acceptance criteria

- [ ] Terminator responsibilities documented; explicit list of what must move
      into the app (if anything).
- [ ] Chosen rate-limiting approach + limits + keying recorded with rationale.
- [ ] Conversation-id ownership decision recorded (signed cookie vs param
      removal) and reflected in follow-up tickets.
- [ ] Follow-up implementation ticket(s) created with acceptance criteria.

## Verification

- Doc review against the three controllers' current behavior.
- Sanity-check chosen library compiles in a scratch branch
  (`deps.get` only — no wiring yet).
