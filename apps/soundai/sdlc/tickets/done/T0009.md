----
title: Server-side TTS inside Elixir (Ortex/ONNX) + POST /api/tts
----

Synthesize text-to-speech **in-process** inside `soundai`, replacing the
standalone Node TTS pod (top-level `tts_server/`, now removed). `soundai`
gains a small TTS seam and a `POST /api/tts` endpoint that returns a playable
WAV to the browser. This is the contract half of the "server" TTS option; the
browser engine is T0010.

There is no separate TTS service anymore: the same `Xenova/mms-tts-spa` VITS
model the browser uses is loaded directly into the Elixir VM with **Ortex**
(ONNX Runtime + `Nx`). The browser never talks to anything but `soundai`.

## Desired architecture

```text
Browser tts_engine.js (T0010)
  |
  | fetch POST /api/tts {text, language}
  v
SoundaiWeb.TTSController#create
  |
  v
Soundai.TTS.synthesize(text)          <- adapter: Soundai.TTS.OrtexServer
  |
  v
Soundai.TTS.OrtexServer (GenServer, FIFO — ONNX sessions are not thread-safe)
  |  lazy-loads priv/tts/model.onnx on first request
  |  VitsTokenizer -> tokenize(text) -> {input_ids, attention_mask}
  |  Ortex.run(model, {ids, mask})   -> waveform f32 {1, n}
  |  Wav.encode_to_map(waveform)      -> %{audio, duration_ms, sample_rate}
  v
%{audio: wav_bytes, content_type: "audio/wav", duration_ms: integer}
  |
  v
200 audio/wav  (X-TTS-Duration-Ms, X-TTS-Model passed through)
```

## Scope

### 1. Configuration

- `config/config.exs` (`:soundai`): `model_path: "tts/model.onnx"` (resolved
  against `priv/`), `max_text_length: 1000`.
- `config/runtime.exs`: `SOUNDAI_TTS_MODEL_PATH` env override; when unset the
  `priv/tts/model.onnx` default applies.
- Access via `Application.get_env(:soundai, Soundai.TTS)` so tests can stub it.
- `Soundai.TTS.enabled?/0` is true only when a model path is configured **and**
  the file exists on disk; `Soundai.Application` starts the `OrtexServer` only
  in that case.

### 2. `Soundai.TTS` seam + `Soundai.TTS.OrtexServer`

- `Soundai.TTS.synthesize(text, language)` → `{:ok, %{audio: binary,
  content_type: "audio/wav", duration_ms: integer}}` or `{:error, reason}`.
  Validation first: `:empty`, `:too_long`, `:invalid` (mirror the
  transcriptions endpoint). The `language` argument is accepted for interface
  parity but the Spanish model ignores it.
- `Soundai.TTS.OrtexServer` is a `GenServer` that owns the loaded `Ortex`
  session (ONNX sessions are not safe for concurrent runs, so all synthesis is
  serialized — a FIFO queue by construction). The model is loaded lazily on the
  first request and cached in state.
- Tokenization mirrors the HF `VitsTokenizer` exactly (see
  `Soundai.TTS.VitsTokenizer`); the WAV encoding lives in `Soundai.TTS.Wav`
  (16 kHz mono 16-bit PCM).
- Tests inject a fake adapter (`:adapter` in `config :soundai, Soundai.TTS`)
  so controller tests never touch ONNX.

### 3. `POST /api/tts` route + controller

- Router (`:api` scope, alongside `/api/transcriptions`): `post "/tts", TTSController, :create`.
- `TTSController#create`:
  - Validate `text`: presence / blank / length cap → `422` JSON error (mirror
    `TranscriptionController` style).
  - Not ready (no model configured/loaded) → `503 {"errors": {"text": "server TTS is not ready"}}`.
  - Call `Soundai.TTS.synthesize/2`; on success → `200` `audio/wav` with
    `X-TTS-Duration-Ms` and `X-TTS-Model` headers set, body = audio bytes. On
    inference failure → `500`.
  - The endpoint is public like `/api/transcriptions` (same security note;
    skip the missing-auth heuristic with the same credo disable comment).

### 4. Security

- Only the assistant's response text travels to `soundai`; the synthesized
  audio returns to the browser. Text is untrusted: validated and length-capped
  exactly like the transcriptions endpoint.
- No secrets, no external service, no credentials anywhere.

## Acceptance criteria

- [ ] No model configured (or file absent) → `POST /api/tts` returns 503 `not ready`.
- [ ] Valid request with the fake adapter returns 200 `audio/wav` with bytes
      and `X-TTS-Duration-Ms` / `X-TTS-Model` headers.
- [ ] Missing/blank/oversized `text` returns 422.
- [ ] `OrtexServer` serializes calls and reports `ready?` only after the model loads.
- [ ] `Soundai.TTS` unit tests cover validation, tokenization, and WAV encoding.
- [ ] Docs describe TTS as in-process Elixir — no references to a running
      `tts_server/` service, its `SOUNDAI_TTS_URL` config, or its `/v1/tts`
      contract remain.
