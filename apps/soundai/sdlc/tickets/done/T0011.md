----
title: Speaking-state watchdog + send timeout (recover from hangs)
----

The voice assistant can get permanently stuck: the state machine waits in
`sending` and `speaking` for a terminal event, and both have unbounded waits —
a `fetch` that never resolves and a TTS `onend` that never fires (the observed
mobile hang / repeated-last-word symptom). Add timeouts so **every** transition
is bounded and always returns to a usable state (PRD §5 graceful failure).

This is the actual hang fix, independent of which TTS engine is selected.

## Scope

### 1. Send timeout (`voice_assistant.js::sendTranscript`)

- `fetch("/api/transcriptions", ...)` currently has no timeout: if the server
  accepts a connection but never responds, the UI sits in `sending` forever.
- Add an `AbortController` + timer (e.g. `SEND_TIMEOUT_MS = 15_000`): on abort,
  treat it like a failed send — quiet note (`Couldn't reach the server —
  transcript kept locally.`), transcript stays visible, `result` state. Never
  the error state.
- Clear/abort the controller when the fetch settles.

### 2. Speaking-state watchdog (`voice_assistant.js::speakResponse`)

- When entering `speaking`, start a watchdog timer; clear it on `onend` or
  `onerror` (both the primary engine and any native fallback).
- Budget: derive from the response length (e.g. `max(SPEAK_MIN_MS = 5_000,
  textLength * 150)`), capped (e.g. `SPEAK_MAX_MS = 30_000`). The point is a
  generous upper bound, not precision.
- On fire while still in `speaking`: `ttsEngine.cancel()`, log a warning
  (`[soundai] speaking timed out; forced result`), set a quiet note (e.g.
  `Speech playback did not finish.`), transition to `result`.
- The watchdog must be cancelled on `pointerdown` too (a new recording already
  cancels speech; a stray timer must not clobber the new `listening` state).

### 3. Consistency

- Verify every state transition that waits on a remote/async event has a bound:
  `sending` (this ticket), `speaking` (this ticket). `transcribing` is bounded
  by the worker (messages always resolve or error).
- No new UI states; timeouts reuse the existing quiet-note + `result` path.

## Acceptance criteria

- [ ] A hanging transcription send resolves after `SEND_TIMEOUT_MS` to `result`
      with a quiet note, transcript visible.
- [ ] If `onend` never fires, the assistant leaves `speaking` within the
      watchdog budget, logs a warning, and shows a quiet note.
- [ ] Normal playback is unaffected: `onend` clears the watchdog before it fires.
- [ ] A new press during a pending timeout does not clobber `listening`.
- [ ] No state transition can stall indefinitely.

## Verification

- Manual browser checks (client flow verified manually per convention):
  - Simulate a hung send (e.g. temporarily point the endpoint at a route that
    never responds) → confirm the ~15 s recovery with the quiet note.
  - Simulate a hung TTS (e.g. an engine whose `onend` is never called) → confirm
    the watchdog fires and the UI returns to `result`.
  - Normal flow → no regression in `sending -> speaking -> result`.
- `cd apps/soundai && mix test` (no Elixir surface beyond existing suites).
