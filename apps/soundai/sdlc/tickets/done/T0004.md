----
title: Send transcribed text to the Phoenix backend
----

After STT produces text in the browser, send that text to the Phoenix backend.

This is the first step away from the current fully client-side, offline-first
architecture: **raw microphone audio still never leaves the browser**, but the
transcribed **text** is now transmitted over the network.

The backend only receives and acknowledges the transcript in this ticket. A
follow-up ticket will relay the text to an LLM (through Needle) and return the
response; this ticket must therefore introduce a clean server-side seam where
that LLM call will slot in, and a client that is already shaped to consume a
future `response` in the JSON envelope.

## Desired architecture

```text
Browser
  |
  | microphone audio (never leaves the browser)
  v
Whisper worker (local STT)
  |
  v
transcribed text
  |
  | POST /api/transcriptions  (fetch, JSON, same origin)
  v
Phoenix -> SoundaiWeb.TranscriptionController (json)
  |
  v
Soundai.Conversation.submit_transcript/1   <-- seam for the future LLM relay
  |
  v
{"ok": true}   (JSON envelope; a future ticket adds the LLM response text)
```

## Scope

### 1. Server: receive the transcript

- Add a JSON endpoint `POST /api/transcriptions` behind the existing (currently
  unused) `:api` pipeline in `apps/soundai/lib/soundai_web/router.ex`. There is
  no LiveView/websocket involved — this is a plain controller action, keeping
  the app's current architecture.
- New `SoundaiWeb.TranscriptionController#create`:
  - Accept `%{"text" => text, "language" => language}` (language optional;
    defaults to the configured STT language).
  - `text` must be a non-empty trimmed string with a maximum length (e.g.
    4000 characters). Reject invalid/missing/oversized input with a JSON error
    (422).
  - On success return `201 {"ok": true}`. Keep the envelope minimal but
    forward-compatible (a follow-up adds `response`, and later possibly a
    `conversation_id`).
- New context module `Soundai.Conversation` with `submit_transcript/1`:
  - For this ticket: normalize and **log the transcript** (`Logger.info`),
    returning `:ok`.
  - This function is the boundary the follow-up LLM ticket will change: the
    controller must call it and nothing else, so the LLM integration stays
    contained in the context.
- The `:api` pipeline has no CSRF plug (JSON `fetch` from the same origin).
  Do **not** put this behind the `:browser` pipeline.

### 2. Client: send the transcript

- In `apps/soundai/assets/js/voice_assistant.js`, once a transcription result
  arrives, POST it to `/api/transcriptions` with `fetch`:
  - `Content-Type: application/json`; body `{ text, language }`.
  - Extend the state machine `transcribing -> sending -> result`:
    - `sending` gets a "Sending…" voice label while the request is in flight.
    - On success show the transcript as today.
    - On failure **keep showing the transcript** and surface a subtle,
      non-blocking notice (e.g. "Transcript not sent — you're offline?") instead
      of an error state.
  - The send must never block or freeze the transcript display.

### 3. Offline & graceful failure

- The app stays offline-first for STT: transcription keeps working with no
  network. Only the send is best-effort.
- `navigator.onLine === false` (or a failed/aborted `fetch`) must simply skip or
  fail the send quietly; it must never transition to the error state on its own.
- No retry/queue mechanism in this ticket (noted for a future milestone).

### 4. Security

- Text is untrusted user input (PRD §14): validate strictly server-side
  (presence, type, length cap).
- The endpoint is public for now (the app has no authentication yet). Note that
  rate limiting should be introduced before any public deployment (PRD §14);
  it is out of scope here.
- Audio is still never transmitted or persisted. The transcript is only logged
  in this ticket.

### 5. Documentation

- Update `apps/soundai/sdlc/TECHNICAL_DESCRIPTION.md`: the app is no longer
  strictly "no Phoenix communication at runtime" — the server now serves the
  HTML/JS/CSS shell **and** accepts one `POST /api/transcriptions` JSON call.
  STT still works fully offline; only the send is best-effort.

## Acceptance criteria

- [ ] `POST /api/transcriptions` accepts a valid `{text, language}` payload and
      returns `201 {"ok": true}`.
- [ ] Missing, blank, or oversized `text` returns a JSON 422 error.
- [ ] `Soundai.Conversation.submit_transcript/1` is the single server-side seam
      that receives the transcript (so the LLM relay is a contained follow-up).
- [ ] A transcription result is POSTed to the endpoint from the browser.
- [ ] The `sending` state ("Sending…") is visible while the request is in
      flight.
- [ ] A failed send still shows the transcript locally and never enters the
      error state.
- [ ] The assistant keeps working (transcription + display) when offline; only
      the send fails gracefully.
- [ ] Raw microphone audio is still never sent to the server.
- [ ] `TECHNICAL_DESCRIPTION.md` reflects the new endpoint.

## Verification

- `cd apps/soundai && mix test` — add `TranscriptionControllerTest` covering
  valid, missing, blank, and oversized text, plus the `{"ok": true}` envelope.
- Manual browser check (consistent with the existing convention of verifying
  the client flow manually):
  - Say a Spanish utterance; confirm the transcript renders and the server
    console logs the received text.
  - Block the network / go offline right before the send; confirm the
    transcript still renders with the non-blocking notice.
- Run `mix precommit` (from the umbrella root) before considering the ticket
  done.
