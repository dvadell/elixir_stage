----
title: Security hardening quick wins (salt, RequestLogger, cookie flags, key redaction)
----

Small, concrete security fixes that don't need the T0019 spike and can land
immediately.

## Scope

### 1. Signing salt out of source code (`soundai_web/endpoint.ex:10`)

`signing_salt: "RxqfOFJ4"` is committed to the repo. Session cookies are
signed (not encrypted), so anyone with the salt can forge valid session
cookies. Move the value to config:

- `config/config.exs`: read from env with a dev fallback;
  `config/runtime.exs` (or `test.exs`) supplies the real value per
  environment, e.g. `System.get_env("SOUNDAI_SIGNING_SALT") || ...`.
- Document salt rotation (invalidates existing sessions — acceptable here).

### 2. Gate LiveDashboard RequestLogger in production (`endpoint.ex:40-42`)

The `Phoenix.LiveDashboard.RequestLogger` plug runs unconditionally, so in
prod anyone setting the `request_logger` query param/cookie can stream recent
request logs (URLs, status, timing — potentially sensitive). Only enable it
when code reloading/dev is on:

```elixir
if code_reloading? do
  plug Phoenix.LiveDashboard.RequestLogger, ...
end
```

(or gate on an explicit config flag if the dashboard is ever wanted in prod
behind auth).

### 3. Cookie flags

- `soundai_conversation` cookie (`transcription_controller.ex`): set
  `secure: true` when serving over HTTPS (derive from endpoint config or a
  config flag so plain-http dev keeps working) and confirm `http_only: true`.
- `assets/js/settings.js` `writeCookie`: append `; Secure` when
  `location.protocol === "https:"`.

### 4. Redact credentials in the smoke task (`mix/tasks/soundai.llm_smoke.ex`)

- `inspect(reason)` on the error path can embed HTTP request details including
  the `Authorization: Bearer <NVIDIA_API_KEY>` header → credential leaked to
  console/logs. Sanitize before printing: strip/drop `:headers`, `:request`,
  and any values containing the configured key; print only the exception
  class/message.
- Also pass a bounded `timeout:` (read `:llm_timeout_ms`, default 30_000) to
  `BranchedLLM.Chat.send_message/3` so a provider hang fails fast instead of
  blocking the terminal forever.

## Tests

- Endpoint/session: test that `@session_options` signing salt comes from

- RequestLogger: in a prod-config simulation (`code_reloading? == false`),

- Smoke task: pure-function test for the sanitizer — feed it an error struct

## Done

- **Salt out of source**: endpoint now resolves `signing_salt:` from
  `config :soundai, SoundaiWeb.Endpoint` at request time via a small
  `signed_session` function plug (`Plug.Session.call/2`), so release builds
  pick up runtime values instead of freezing compile-time ones.
  `config/config.exs` reads `SOUNDAI_SIGNING_SALT` with a public throwaway
  dev/test fallback; prod (`config/runtime.exs`) prefers `SOUNDAI_SIGNING_SALT`
  and otherwise derives a stable salt from `SECRET_KEY_BASE` (existing
  docker-compose deployments boot without new required env vars). Rotation
  invalidates sessions — documented in endpoint/config comments, README and
  TECH_DESCRIPTION. Verified live under `MIX_ENV=prod` (derived value +
  explicit override both resolve).
- **RequestLogger gated**: `Phoenix.LiveDashboard.RequestLogger` moved inside
  the existing `if code_reloading? do ... end` block, so it compiles away in
  test/prod. Regression test inspects the compiled beam's atom table
  (resolved from the build's ebin dir, cover-safe) and asserts the plug module
  is absent when code reloading is off.
- **Cookie flags**: new shared `SoundaiWeb.ConversationCookie`
  (`http_only: true`, `SameSite=Lax`, 7-day max-age, `secure:` derived from
  the endpoint's configured URL scheme — production sets `scheme: "https"`
  even behind an SSL-terminating proxy, where Plug's conn-scheme auto-Secure
  never fires). Both conversation controllers use it. `settings.js`
  `writeCookie` appends `; Secure` on HTTPS. Tests assert HttpOnly always,
  Secure iff https-configured (unit + controller level).
  - Note: Plug already defaulted the cookie to HttpOnly, which silently broke
    the client's "Nueva conversación" (JS cannot delete HttpOnly cookies).
    The button now schedules `reset: true` on the next transcript POST
    (server-side reset from T0016), keeping the offline-friendly behavior;
    TECH_DESCRIPTION §3.1/§4.1 updated.
- **Smoke task redaction + timeout**: `mix soundai.llm_smoke` now calls the
  LLM through an injectable adapter (default `Soundai.Conversation.LLM`) with
  `timeout: llm_timeout_ms` (default 30 s) and prints errors through
  `sanitize_error/2`: drops HTTP plumbing keys (`headers`, `request`,
  authorization/api-key entries — atom and binary header names), redacts any
  string containing the configured key wholesale, scrubs embedded
  "Bearer <token>" patterns, renders exceptions as `"Module: message"`.
  Pure function, unit-tested.
- Manual verification: ran with a bogus `NVIDIA_API_KEY` — the key never
  appears anywhere in the output (grep count 0), error path exits promptly.
  Residual: branched_llm/req_llm log their own internal warning lines during
  failures; today they carry response headers only (no request auth headers),
  and they are outside this task's control.
- Checks (umbrella root): `mix precommit` green — format,
  `compile --warnings-as-errors`, credo --strict (0 warnings), dialyzer
  (0 errors), tests 178 soundai + 19 soundpanel + 7 watchtower;
  `mix assets.build` after the JS changes; grep for the old salt clean
  outside `done/`.

## Review follow-up (`ocr review`)

- **Fixed [bug · high]**: `sanitize_error(reason)` recursed infinitely when no
  API key was configured — the `nil` sentinel clause re-dispatched on
  `api_key() == nil`, stack-overflowing exactly in the "key missing" error
  path this task diagnoses. The sentinel is now resolved once
  (`api_key() || ""`: empty string = "no known secret", bearer scrub still
  applies). Two regression tests cover the unset-`{:system, var}` and
  no-providers cases.
- **Declined [security · medium]**: reviewer suggested failing fast instead of
  committing a dev/test signing-salt fallback. Kept as-is: it mirrors Phoenix's
  own convention (generated dev/test configs ship throwaway secrets), prod is
  always overridden by `config/runtime.exs` (the only supported deployment
  path — releases), and failing fast would break plain `mix phx.server` /
  `mix test` for every developer for zero real-world gain; a dev-mode server
  on a "production box" already runs with dev database credentials, debug
  errors and code reloading, so it isn't production by any other measure.
  Documented as public-on-purpose in config comments and README.
- Coverage note: the review run was partial (5 of 13 subtasks failed on
  provider timeouts — `conversation_cookie.ex`, `endpoint.ex` and the three
  new test files were not fully reviewed).
