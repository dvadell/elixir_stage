----
title: Echo the transcript back and speak it with the browser's native TTS
----

After STT produces text in the browser and it is sent to the Phoenix backend
(T0004), the server now **echoes the text back** in the JSON envelope, and the
browser **speaks it aloud using the native Web Speech API** (`speechSynthesis`).
No audio is synthesized on the server in this ticket.

The point of the round trip is **fidelity**: the browser must speak exactly what
the server returns, not the local transcript. Today the server just echoes the
transcript; when the LLM relay lands (through Needle), the same `response` field
will carry the LLM's answer and this client code will speak it unchanged.
Getting the round trip working now means the future LLM ticket only has to change
what the server puts into `response`.

## Desired architecture

```text
Browser
  |
  | microphone audio (never leaves the browser)
  v
Whisper worker (local STT)
  |
  v
"Buenos días"
  |
  | POST /api/transcriptions  (fetch, JSON, same origin)
  v
Phoenix -> SoundaiWeb.TranscriptionController
  |
  v
Soundai.Conversation.submit_transcript/1   <-- seam for the future LLM relay
  |
  v
{"ok": true, "response": "Buenos días", "language": "spanish"}
  |
  v
Browser native speechSynthesis -> speaker
```

## Scope

### 1. Server: echo the transcript back

- `Soundai.Conversation.submit_transcript/1` returns `{:ok, response}` where, for
  now, `response == trimmed text`. This function remains the single boundary the
  follow-up LLM ticket will change; the controller must call it and nothing else.
- `TranscriptionController#create` returns `201` with the forward-compatible
  envelope:

  ```json
  {"ok": true, "response": "Buenos días", "language": "spanish"}
  ```

  The `response` key is the slot that will later carry the LLM reply. Missing,
  blank, or oversized text keeps returning the existing `422` error envelope.

### 2. Client: speak what the server returns

- In `apps/soundai/assets/js/voice_assistant.js`, `sendTranscript/1`:
  - On success, if `data.response` is a non-empty string, speak it.
  - Use the native `speechSynthesis` API (no server audio, no provider):
    - `new SpeechSynthesisUtterance(response)`.
    - Set `utterance.lang` from the STT language (e.g. `spanish` → `es-ES`) and
      prefer a matching voice from `speechSynthesis.getVoices()`.
  - If `data.response` is missing/blank or `speechSynthesis` is unsupported, keep
    showing the transcript with a quiet note — **never** the error state.
- Extend the state machine: `... sending -> speaking -> result`:
  - `speaking` gets a "Speaking…" voice label while the utterance plays.
  - `utterance.onend` transitions back to `result` ("Tap to talk again").
  - Starting a new recording (`pointerdown`) calls `speechSynthesis.cancel()` so
    the user can interrupt the assistant mid-speech (PRD §18 interruptions, kept
    minimal here: stop old audio, start recording).

### 3. Graceful failure & offline

- Offline (`navigator.onLine === false`) keeps skipping the POST (T0004
  behavior): the transcript shows as today and nothing is spoken.
- The send remains best-effort; a failed `fetch` means no `response` to speak —
  transcript stays visible, quiet note.
- TTS is purely client-side, so there is no TTS provider to fail. Browser
  playback quirks (autoplay policy, unsupported `speechSynthesis`) degrade to a
  quiet note and leave the UI usable.

### 4. Security

- Only the transcribed text travels; raw microphone audio never leaves the
  browser (PRD §11).
- The server returns the same text it received — no new data exposure.
- `speechSynthesis` runs locally; no audio leaves the device.

### 5. Documentation

- Update `apps/soundai/sdlc/TECHNICAL_DESCRIPTION.md`: the endpoint now returns a
  `response` field echoing the transcript, and the client speaks the server's
  text with native `speechSynthesis` (`sending -> speaking -> result`).

## Acceptance criteria

- [ ] `POST /api/transcriptions` returns `201` with
      `{"ok": true, "response": <text>, "language": ...}` echoing the (trimmed)
      transcript.
- [ ] `Soundai.Conversation.submit_transcript/1` remains the single server-side
      seam that produces the `response`.
- [ ] The browser speaks the server-returned `response` aloud via
      `speechSynthesis` (not the local transcript directly).
- [ ] The `speaking` state ("Speaking…") is shown while the utterance plays and
      returns to `result` afterwards.
- [ ] Starting a new recording stops the currently playing utterance.
- [ ] A missing/blank `response` or an unsupported `speechSynthesis` degrades to
      transcript + quiet note (no error state).
- [ ] Offline still works for STT + transcript display; nothing is spoken.
- [ ] Raw microphone audio is still never sent to the server.
- [ ] `TECHNICAL_DESCRIPTION.md` reflects the new round trip.

## Verification

- `cd apps/soundai && mix test` — update `TranscriptionControllerTest` to assert
  the `response` echo in addition to the existing valid/invalid cases.
- Manual browser check (consistent with the existing convention of verifying the
  client flow manually):
  - Say a Spanish utterance; confirm the transcript renders and the assistant
    says it back ("Buenos días") using a Spanish voice.
  - Tap the button while the assistant is speaking; confirm playback stops and a
    new recording starts.
  - Go offline right before the send; confirm the transcript still renders with
    the offline note and nothing is spoken.
- Run `mix precommit` (from the umbrella root) before considering the ticket
