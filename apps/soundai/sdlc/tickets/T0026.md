----
title: Conversation lifecycle semantics — reset race & context-advance-on-failure
----

Two behavioral edge cases in the conversation flow are undefined today. This
ticket makes them explicit decisions, implements them, and pins them with
tests. (The ownership/security dimension of client-controlled ids is tracked
in the T0019 spike.)

## Scope

### 1. Reset vs concurrent requests (`conversation_audio_controller.ex:61-65`, same pattern in transcription controller)

`resolve_conversation_id/2` unconditionally deletes the stored context for
the stale id before creating a fresh one. If two requests share the cookie
(e.g. double-fire, or a retry racing a reset), the reset deletes the context
out from under the in-flight turn, and deletion isn't atomic with the fresh
id creation.

Options to evaluate:

- Delete only when the incoming id matches the cookie value;
- Tombstone/grace window instead of hard delete;
- Accept single-client assumption pre-auth, but document it (link T0019).

Implement the chosen option; at minimum document the guarantee clients get.

### 2. Cookie/context advance on TTS failure (`conversation_audio_controller.ex:88-93`)

The cookie is set and server-side context advances *before* synthesis runs,
so a failed TTS turn still consumes conversation context; retrying the same
text after failure continues from the advanced state (the user's utterance
was already answered by the LLM — only speech failed). Confirm this is
intended:

- If yes: document it (client note already says "el servidor no pudo generar
  audio"; add TECH_DESCRIPTION gotcha).
- If no: only persist context/cookie after successful synthesis (requires
  deferring `Store.put` until WAV bytes exist).

### 3. Docs

Record both decisions in TECH_DESCRIPTION §12 (gotchas) so future changes
don't silently flip semantics.

## Tests

- Reset semantics: submit turn A, then issue reset while simulating a second
  in-flight submit on the same cookie (interleave calls against the fake
  adapter) — assert the documented outcome (either A's context survives or
  the delete wins deterministically; no crash, no orphaned id).
- TTS-failure flow: fake TTS adapter returning `{:error, _}` → next turn's
  LLM context either contains or excludes the failed turn exactly as decided;
  cookie state matches the decision.
- Reset returns fresh id and old id no longer resolvable (existing tests kept
  green).

## Acceptance criteria

- [ ] Both behaviors are implemented decisions, not accidents.
- [ ] Documented in TECH_DESCRIPTION.
- [ ] Regression tests pin each decision.
