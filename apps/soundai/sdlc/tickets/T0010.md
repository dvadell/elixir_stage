----
title: Browser "server" TTS engine + /settings option
----

Add the **server** TTS engine to the browser: a new engine in `tts_engine.js`
that calls `soundai`'s `POST /api/tts` (T0009), decodes the returned WAV, and
plays it via Web Audio — bypassing `speechSynthesis` and the local VITS worker
entirely. Plus the `/settings` entry. This is the option the user selects to
test server-side TTS on mobile.

## Desired architecture

```text
voice_assistant.js speakResponse(responseText)
  |
  v
createTTSEngine("server") -> ServerTTSEngine (tts_engine.js)
  | fetch POST /api/tts {text, language}    (AbortController)
  | response.arrayBuffer()
  | AudioContext.decodeAudioData(buffer)     (WAV)
  v
AudioBufferSourceNode -> speaker  -> onended -> onend -> "result"
  |-- cancel(): abort fetch + stop source
  `-- failure -> onerror -> voice_assistant falls back to native (quiet note)
```

## Scope

### 1. Server engine (`assets/js/tts_engine.js`)

- Register id `"server"` in the registry (one line via the existing mechanism).
- `ServerTTSEngine` implements the engine interface:
  - `init()` → resolves immediately (no model preload); `isReady()` → true
    once constructed. The server owns the model.
  - `speak(text, language, {onend, onerror})`:
    - `fetch("/api/tts", {method: "POST", headers: {"Content-Type":
      "application/json"}, body: JSON.stringify({text, language}),
      signal: abortController.signal})`.
    - On non-200 → `onerror` (surface the JSON error message).
    - On 200 → `arrayBuffer()` → `decodeAudioData` on a dedicated
      `AudioContext` (reuse the playback pattern from
      `TransformersTTSEngine._playAudio`) → play → `onended` → `onend`.
    - Guard against stale responses (generation counter like the transformers
      engine) so a cancelled request never plays late audio.
  - `cancel()` → abort the in-flight fetch and stop the source node.
- Keep the `server` engine **last-ish but native last** in precedence rules is
  unaffected — engines resolve by id only.

### 2. `voice_assistant.js` wiring

- `ensureTTSPreload()` must treat `"server"` like `"native"`: **no model
  preload, no worker** (skip `init`/`detectDevice`). The existing fallback
  logic in `speakResponse` (`config.tts !== "native"` → fall back to native on
  failure) already covers `"server"` unchanged — keep it.
- No other controller changes: `speak`/`cancel` go through the engine like any
  other engine.

### 3. `/settings` option

- `SettingsHTML @tts_models`: add
  `{"server", gettext("Servidor (remoto)"), gettext("Synthesized on the server. Requires the server-side TTS service to be deployed.")}`.
  `native` **must remain the last option**.
- Cookie persistence and precedence (`?tts= > soundai_tts cookie > default`)
  are already generic — no `settings.js` change needed.

### 4. Service worker

- `/api/tts` is a POST; the SW only handles GET (`if (request.method !==
  "GET") return;`) so it is never cached — no SW logic change.
- The `/settings` shell changes (new option) → **bump `CACHE_NAME`** to
  `soundai-shell-v3` in `priv/static/service_worker.js` (per §12 convention).

### 5. Security & privacy

- Only the response text travels to `soundai`'s `/api/tts`; the audio returns
  and is played locally. The pod never sees the browser.

## Acceptance criteria

- [ ] Selecting `server` in `/settings` persists via `soundai_tts`; `/` uses it.
- [ ] With the pod up, the assistant speaks the response audio via Web Audio
      (no `speechSynthesis`, no VITS worker) and `onend` → `result` works.
- [ ] With the pod down (or `/api/tts` 503), the assistant falls back to the
      native engine with a quiet note — never the error state.
- [ ] A new press while server audio plays cancels fetch + playback
      (`ttsEngine.cancel()`).
- [ ] Stale audio from a cancelled request never plays.
- [ ] `native` is still the last option in `/settings`.
- [ ] `CACHE_NAME` bumped.
