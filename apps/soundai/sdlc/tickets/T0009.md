----
title: Server-side TTS client + POST /api/tts proxy
----

Add the Elixir side of server-side TTS: `soundai` gains a small client that
calls the standalone Node TTS pod (top-level `tts_server/`, its own k8s Deployment)
and a `POST /api/tts` endpoint that proxies the audio back to the browser. This
is the contract half of the "server" TTS option; the browser engine is T0010.

The TTS pod is **internal** (ClusterIP only). The browser never talks to it —
it calls `soundai`, which relays.

## Desired architecture

```text
Browser tts_engine.js (T0010)
  |
  | fetch POST /api/tts {text, language}
  v
SoundaiWeb.TTSController#create
  |
  v
Soundai.TTS.synthesize(text, language)     <- Req (required HTTP client)
  |      POST http://tts-server:8080/v1/tts      (SOUNDAI_TTS_URL)
  v
{audio: wav_bytes, headers: X-TTS-* }
  |
  v
200 audio/wav  (Content-Type + X-TTS-* passed through)
```

## Scope

### 1. Configuration

- `config/runtime.exs` (`:soundai`): `tts_url` from `System.get_env("SOUNDAI_TTS_URL")`
  (default `nil` = server TTS disabled). Also `tts_timeout` from
  `SOUNDAI_TTS_TIMEOUT_MS` (default 15 s) and optional `tts_max_text_length`
  (default 1000, matching the pod).
- Access via `Application.get_env(:soundai, :tts_url)` so tests can stub it.

### 2. `Soundai.TTS` client

- `synthesize(text, language)` → `{:ok, %{audio: binary, content_type: binary}}`
  or `{:error, reason}`.
- Uses **Req**: `Req.post!(base <> "/v1/tts", json: %{text: text, language:
  language}, receive_timeout: tts_timeout)`.
- Maps failures: `:not_configured` (no URL), `:timeout`, `:upstream`
  (non-200, include status), `:invalid` (bad text).
- `Logger.info` timing (request → response, bytes) — this is the mobile
  debugging instrument (per `tts_server/sdlc/TECHNICAL_NOTES.md` §7, the
  top-level `tts_server/` project).
- Pure function module (no GenServer needed); the pod's queue handles
  concurrency. Wrap in a mockable seam for tests (call the client through a
  named function that tests can override, or accept the URL as an argument).

### 3. `POST /api/tts` route + controller

- Router (`:api` scope, alongside `/api/transcriptions`): `post "/tts", TTSController, :create`.
- `TTSController#create`:
  - Validate `text`: presence / blank / length cap → `422` JSON error (mirror
    `TranscriptionController` style).
  - Not configured → `503 {"errors": {"tts": "server TTS is not configured"}}`.
  - Call `Soundai.TTS.synthesize/2`; on success → `200` with the upstream
    `Content-Type` and `X-TTS-Duration-Ms`/`X-TTS-Model` passed through, body =
    audio bytes. On error → `502` (upstream failure) / `504` (timeout) JSON.
  - The endpoint is public like `/api/transcriptions` (same security note;
    skip the missing-auth heuristic with the same credo disable comment).

### 4. Security

- The pod is internal-only; `soundai` is the only caller. Text is untrusted:
  validated and length-capped exactly like the transcriptions endpoint.
- No secrets: the URL carries no credentials.

## Acceptance criteria

- [ ] `SOUNDAI_TTS_URL` unset → `POST /api/tts` returns 503 `not configured`.
- [ ] Valid request with a stubbed client returns 200 `audio/wav` with bytes
      passed through.
- [ ] Missing/blank/oversized `text` returns 422.
- [ ] Upstream 4xx/5xx maps to 502; timeout maps to 504.
- [ ] Requests to the pod are made with Req and carry the documented timeout.
- [ ] `Logger` records a timing line per synthesis.

## Verification

- `mix test` with `TTSControllerTest`: stub `Soundai.TTS` (or inject the URL)
  to cover 200/503/422/502/504 paths.
- With the pod running locally (`node src/server.mjs`), set
  `SOUNDAI_TTS_URL=http://localhost:8080`, start `mix phx.server`, and
  `curl -XPOST :4002/api/tts -d '{"text":"Hola"}' -o hola.wav` — assert the WAV.
- Run `mix precommit` (umbrella root) before considering the ticket done.
