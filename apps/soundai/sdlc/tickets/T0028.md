----
title: Supervision & runtime-config lifecycle for the TTS server
----

The TTS child's lifecycle is decided once at boot and diverges from how
config changes are handled elsewhere (`application.ex:20,37-40`).

## Scope

### 1. Start order

`Soundai.TTS.OrtexServer` is appended *after* `SoundaiWeb.Endpoint`, so the
HTTP surface can accept `/api/tts` requests before the supervised GenServer
exists (currently saved only by the `:not_ready` fallback). Start the TTS
child before the Endpoint in the supervision list.

### 2. Boot-time-only enablement

`enabled?/0` does a `File.exists?` check at boot only: a model file that
appears later never gets a server without a full restart. Prefer **always
starting the child** and letting readiness be determined lazily by
`ensure_model/1` (with T0021's failure caching making repeated misses cheap),
or keep the boot-time gate but document it explicitly. Pick one; lazy-start
is recommended because it also removes the conditional-supervision branch
that makes tests environment-dependent (see T0037).

### 3. `config_change/3`

Only Endpoint config is reloaded; TTS/Conversation runtime config is ignored,
so a changed `model_path` leaves a stale OrtexServer running (or none).
Either:

- handle `changed` keys for `Soundai.TTS` (restart the child with new
  config), or
- document boot-time-only behavior and log a warning when TTS config changes
  at runtime.

## Tests

- Unit-test the pure children-building function for ordering (TTS before
  Endpoint) under both enabled/disabled configs.
- OrtexServer started via `start_supervised!` without a model file →
  `synthesize` returns `{:error, :not_ready}` (no crash), covering the
  always-start path.
- Manual/dev-console verification of `config_change`: change
  `model_path` via `Application.put_env` + `Application.config_change`
  simulation, assert documented behavior (restart or warning log).

## Acceptance criteria

- [ ] The API can't receive TTS requests before the owning process exists.
- [ ] Model appearing after boot is either picked up or the limitation is
      documented in code + TECH_DESCRIPTION.
- [ ] Runtime config-change behavior is implemented or explicitly logged.
