----
title: LLM error handling, timeouts & conversation reset
----

Polish the failure and lifecycle surface of the new LLM conversation: bounded
LLM latency, friendly Spanish errors for every failure the PRD calls out (§5,
§13), and a way for the user to start a fresh conversation.

## Scope

### 1. Bounded LLM latency

- `Soundai.Conversation` must pass a `timeout:` to the LLM adapter (default
  30 s, configurable under `config :soundai, Soundai.Conversation`), relying on
  BL-03's per-call timeout. A timeout must surface as `{:error, :llm_timeout}`.
- Keep `max_tokens` (e.g. 300) and the response-length cap (T0013) — these
  bound TTS latency too. Document the effective latency budget
  (STT + LLM timeout + TTS) in TECH_DESCRIPTION.

### 2. Error mapping & friendly messages

- Define a small error vocabulary in `Soundai.Conversation`:
  `:llm_unavailable` (network/provider), `:llm_timeout`, `:empty`,
  `:too_long`, `:invalid`. Map to HTTP in both controllers (T0013/T0014) as
  JSON, and map to a **short Spanish** message the client can show as a quiet
  note under the transcript (never the error state), e.g.:
  - LLM unavailable: "No pude conectar con el asistente. Inténtalo otra vez."
  - Timeout: "El asistente tardó demasiado. Inténtalo otra vez."
  - TTS unavailable (audio mode): "El servidor no pudo generar audio."
- The client (T0015) renders these notes; keep the "offline" note behavior.

### 3. Conversation reset

- Add a reset affordance so a stale conversation (or a confused follow-up) can
  be cleared without reloading:
  - Client: when the user starts a new session with no cookie, the server
    already creates a fresh context; add an explicit control (e.g. a small
    "Nueva conversación" button on the voice page) that clears the
    `soundai_conversation` cookie (`document.cookie = "...; max-age=0"`) and
    optionally resets UI state to `result`.
  - Server: `submit_transcript/2` already treats unknown ids as new; also
    support `reset: true` in the body (deletes the stored context, returns a
    fresh id) for robustness. Tests for both.

### 4. Store hygiene

- Confirm TTL cleanup actually bounds memory under load (unit test; no sleeps —
  drive the store directly). Log store size at debug level for ops.
- Note PRD §14 out of scope: authentication + rate limiting still pending
  before any public deployment (add to README status, not implemented here).

## Implementation notes

- Bounded latency was already in place from T0013: `submit_transcript/2` passes
  `timeout: llm_timeout_ms` (default 30 s) to the adapter and maps timeouts to
  `:llm_timeout`. `max_tokens` at the `Chat.send_message/3` level is not
  supported (BL-03), so TTS latency is bounded by the 500-char `max_response_chars`
  cap instead. Latency budget + error vocabulary documented in TECH_DESCRIPTION.
- `reset: true` is honored server-side in **both** controllers (deletes the
  stored context for the incoming id, returns a fresh id and replaces the
  cookie); the client's "Nueva conversación" button clears the cookie directly
  (the next turn then naturally creates a fresh context).
- Spanish quiet notes are rendered client-side from stable HTTP status codes
  (504 → "El asistente tardó demasiado…", 502/network → "No pude conectar…",
  503 → "El servidor no pudo generar audio…"); the transcript always stays
  visible and the error state is never entered.
- `Soundai.Conversation.Store` logs a debug line with removed/remaining counts
  when a sweep drops entries (memory is bounded by the idle TTL, verified by the
  T0013 sweep unit test).
