----
title: Browser TTS engine — readiness semantics & message races
----

`assets/js/tts_engine.js` marks engines "ready" when they aren't and has
listener/postMessage races that can hang an utterance silently.

## Scope

### 1. Native engine readiness (`tts_engine.js:41-44`)

The 2 s timeout fallback unconditionally sets `_ready = true` even if
`getVoices()` never returned voices; `speak()` then proceeds against an
unusable API. Resolve ready only on a non-empty voice list, clear the pending
timeout when `voiceschanged` fires, and keep the timeout as a *failure* path
(`_ready = false`, surface a "no voices" error to the caller) rather than a
success path.

### 2. Server endpoint check (`tts_engine.js:289-294`)

`_checkEndpoint()` treats any HTTP response (400/500 included) as "ready".
Only 2xx/3xx should mark ready; server errors mean not-ready so the picker's
fallback logic behaves honestly.

### 3. Listener-after-post race (`tts_engine.js:185-188`)

In `speak()`, the `synthesize` message is posted before the `'message'`
listener is attached — a fast response (immediate error, cached audio) is
silently dropped and the utterance hangs. Attach the listener before
`postMessage`.

### 4. Stale error delivery (`tts_engine.js:194-195`)

The `error` branch lacks the id guard the audio branch has; errors from a
previous job can fail the current utterance. Guard with `msg.id === id`.

### 5. Unhandled `ctx.resume()` rejection (`tts_engine.js:211-213`, same in ServerTTSEngine)

`ctx.resume()` is unawaited; autoplay-policy rejections become unhandled
promise rejections and playback silently never starts. Await/catch it and
route the failure through the normal `onerror` path.

Confirm-only items (add comments, no behavior change expected): the
best-effort `{type:"cancel"}` semantics, and the interleaved-mono layout
assumption for worker PCM in `_playAudio`.

## Tests

No JS unit harness exists for these modules yet; ship with a manual matrix +
console-error sweep:

- Block microphone-independent TTS: set OS/browser to have zero
  speechSynthesis voices (or emulate) → UI shows the quiet note instead of
  hanging "Speaking…" forever.
- Stop the Phoenix server → selecting "Servidor" mode must mark the endpoint
  not-ready and fall back to text mode (not speak into a 500).
- Rapid double-press (cancel + re-synthesize) → no cross-job error leakage;
  each press resolves exactly one onend/onerror.
- First user gesture without prior interaction (autoplay policy) → clean
  error/note, zero unhandled rejections in console.

## Acceptance criteria

- [ ] `_ready` only ever true with a usable engine; failures surface via the
      existing quiet-note path.
- [ ] No listener/postMessage ordering race; no stale-id error handling.
- [ ] Zero unhandled promise rejections during the manual matrix.
